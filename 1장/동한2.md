# 1.1

DAO = Data Access Object -> 데이터에 접근하는 일만 하는 객체
이유는 프로그램을 짤 때 역할을 분담하기 위해서, DB에서 데이터 꺼내오거나 저장하는 일만 딱 떼어서 전담 객체를 만든 게 DAO이다.

### 분리를 하는 이유?
- 분리를 해놓지 않으면 나중에 리팩토링할 때 문제가 생김
- 코드가 깔끔하지 않음

## 1.1.1 JDBC
- 자바로 DB 다루는 표준 방법

### JDBC 코드의 패턴 네 가지
- DB 연결
- SQL을 담을 statement 만들기
- SQL 실행
- 연결 / 자원 닫기


# 1.2

1.1.1에 나온 코드에 연결코드가 중복된다는 문제점 발견, 해결 단계

## 1.2.1 관심사의 분리
- 하나의 클래스나 메서드는 한 가지의 관심사만 가져야 한다

## 1.2.3
만약 UserDao를 여러 회사/개발자들이 나눠 쓰는데, 각자 DB 연결 방식이 다르다면? 이라는 의문을 갖고 시작
- Ex) N사는 자기들만의 DB 연결 방식을 사용하고 싶음 -> 근데 UserDao 소스 코드 자체는 공유 라이브러리라서 함부로 수정하면 안 됨 -> 상속을 사용하면 해결

### 템플릿 메서드 패턴
- 부모 클래스가 전체적인 템플릿을 정해두고, 그중 일부는 자식 클래스가 구현하도록 비워둠

### 상속의 문제점
- 자바는 다중상속이 안 됨
- 상속으로 묶여있으면 너무 강하게 결합되어 코드가 바뀌면 자식 클래스들도 영향을 받음
- 연결 방식을 추가할 때마다 매번 새로운 서브 클래스를 만들어야 함


# 1.3

상속의 문제점을 해결하기 위한 방법들을 찾아보자

상속 대신 아예 별도의 클래스로 떼어내자 (완전히 독립적인 클래스로 만들기)
-> 만약 N사가 자기만의 커넥션 클래스를 쓰고 싶다면? -> UserDao 코드를 직접 고쳐야 하는 문제점이 생김 -> 즉 현재 부품을 바꾸고 싶으면 부품만 갈아 끼우면 되는데, 본체 자체를 뜯어서 고쳐야 하는 문제가 생김

## 1.3.2
UserDao 코드 안에 구체적인 클래스 이름과 메서드 이름이 박혀 있어서, 다른 커넥션 클래스로 바꾸려면 UserDao 코드를 직접 고쳐야 하는 문제점으로 시작
-> 해결하기 위해 UserDao가 구체 클래스를 직접 알지 못하게 하자는 생각 -> 인터페이스 사용 -> 메서드 이름은 이걸로 통일되어 해결됨

> 인터페이스: 이런 기능을 꼭 가지고 있어야 한다는 규약, 실제 동작 코드는 없고 이름표만 있음

## 1.3.3
인터페이스를 사용해도 문제가 생김
- 어떤 회사의 객체(구현체)를 쓸지를 UserDao 자기 자신이 결정하는 게 문제 -> 이 결정을 UserDao에서 빼자는 생각 -> 관계설정 책임의 분리로 해결

어떤 구현체를 쓸지는 UserDao가 정하지 말고, UserDao를 사용하는 외부 코드가 정해서 **생성자 파라미터**로 넘겨주자라는 해결방안

## 1.3.4
현재 상속 -> 클래스 분리 -> 인터페이스 -> 인터페이스 + 생성자 파라미터로 객체 주입, 이 과정에서 매우 중요한 원칙과 패턴이 존재

**1. 개방 폐쇄 원칙 (OCP)**
- 기능을 확장하는 데는 열려있고, 기존 코드를 변경하는 데에는 닫혀있어야 한다

**2. 높은 응집도, 낮은 결합도**
- 높은 응집도: 한 가지 일에만 집중 = 응집도 높음
- 낮은 결합도: 인터페이스만 알지 구현체 클래스는 모름 -> 서로 느슨하게 연결됨 = 결합도 낮음
- 좋은 설계의 목표 = 높은 응집도 + 낮은 결합도

**3. 전략 패턴**
- 컨텍스트가 자신의 로직 중 일부를 인터페이스로 감춘 뒤, 감춘 객체에게 넘기고 그 객체를 자유롭게 바꿔 끼울 수 있게 만든 디자인 패턴

> 컨텍스트: 일을 시키는 주체


# 1.4

## 1.4.1
UserDao를 사용하려면 매번 인터페이스 구현체를 만들고, 나중에 다른 인터페이스로 바꿀 때 모든 곳을 다 고쳐야 하는 문제점 발생
-> 해결방안으로 어떤 객체를 만들고 어떻게 연결할지 결정하는 일만 하는 클래스를 만들기로 함

## 1.4.2
각 Dao들도 DB 커넥션이 각각 필요한데, 여러 군데가 중복될 때 바꾸고 싶으면 모두 다 바꿔줘야 하는 문제가 있음
-> 오브젝트 팩토리 활용 - DAO가 여러 개로 늘어나도, 커넥션 만드는 로직을 안에서 한 곳(메서드)으로 모아서 중복을 없앤 것
-> 커넥션 방식을 바꾸고 싶으면 이 메서드 하나만 고치면 전체 DAO에 다 반영


# 1.5

우리가 직접 만든 클래스가 객체를 만들고 조립하는 일을 담당 -> 우리가 직접 만듦
스프링 -> 객체를 만들고 조립하는 일을 대신 해줌

## 1.5.1
스프링에는 **애플리케이션 컨텍스트**라는 기능이 있음 -> 스프링의 핵심 부품
어노테이션 두 개만 붙이면(@) 스프링이 이 클래스를 객체 설정 정보로 인식함 -> 이후 스프링에게 객체를 요청하면 스프링이 대신 만들어서 줌

> **빈(Bean)**: 스프링을 관리하는 객체 (new를 직접 하지 않아도 스프링이 알아서 만들어서 관리해주는 객체)
> 
> **빈 팩토리(BeanFactory)**: 빈을 생성하고 관계를 설정해주는 기능을 담당하는 스프링의 가장 기본적인 컨테이너
>
> **애플리케이션컨텍스트(ApplicationContext)**: 빈 팩토리를 확장한 것. 스프링이 제공하는 실제 팩토리
>
> **설정정보(configuration)**: `@Configuration`이 붙은 클래스처럼, "어떤 빈을 어떻게 만들지" 정의해놓은 것
> 

### 왜 굳이 스프링을 써야 할까?
- 객체를 어떻게 만들지 규칙만 정해주면 나머지는 스프링이 다 알아서 해줌
- 우리가 코드를 직접 관리 안 해도 됨
- 스프링이 제공하는 다양한 부가기능도 덤으로 받음
