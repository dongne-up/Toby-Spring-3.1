# Chapter 3

DI를 책에서 나온 내용말고 잘 이해가 되지 않아서 다시한번 처음부터 정리 하게 되었다.

## 의존관계

우선 의존 관계에 대해서 알아야한다.

의존관계란?

A가 일을 하려면 B가 꼭 있어야 할 때 A는 B에 의존한다라고 말한다.

즉 어떤 클래스(객체)가 자기 할 일을 하기위해 다른 클래스(객체)를 사용한다면 앞 클래스는 뒤 클래스에 의존한다.

### 그런데 의존 관계를 내가 직접 만들면 생기는 문제

예를 들어서 핸드폰 클래스가 있고, 얘가 통화를 하려면 배터리가 필요하다는 코드를 간단하게 짜면

```notion
class Phone {
    Battery battery = new SamsungBattery(); // Phone이 직접 배터리를 만든다
}
```

이렇다고 했을 때 생기는 문제는 핸드폰 클래스 안에 new를 직접 못박았기 때문이다. 이게 무슨말이냐면 나중에 만약 LG배터리를 사용해야한다면 핸드폰 클래스의 코드를 뜯어서 고쳐야하는데 **이렇게 한쪽이 다른 쪽의 구체적인 내용을 직접 알고 꽉 붙들고 있는 상태를 강하게 결합돼 있다(tight coupling)**고 표현함..

문제점 1

- 바꿔 끼우기가 어려움 - 배터리 종류를 바꾸려면 핸드폰 코드를 다시 짜야함

문제점 2

- 테스트하기가 어려움 - 핸드폰이 잘 작동하는지 테스트하고 싶은데, 매번 진짜 배터리가 있어야만(예를 들면 실제 DB 연결 같은 무거운 것) 테스트할 수 있다. 가짜 배터리로 잠깐 테스트해보고 싶어도 안 됨

### 해결 방안 - 인터페이스로 한 겹 감싸보자

문제를 해결하기 위해 핸드폰이 삼성배터리라는 구체적인 것 대신, 배터리라는 **인터페이스**(이런 기능을 갖고 있어야 한다는 약속, 규격을 정해놓은 것)만 알게 만듬.

예를 들어

```notion
interface Battery { void supplyPower(); }

class Phone {
    Battery battery; // 이제 어떤 회사 배터리인지는 모른다, Battery라는 자격만 본다
}
```

근데 여기서 궁금한점 - 인터페이스만 사용하면 실제로 쓸 물건이 없음. 누군가는 결국 삼성 배터리든 LG배터리든 진짜 물건을 만들어서 핸드폰에 끼워줘야함.

> Q. 그러면 인터페이스로 만든건 가짜인가?
>

> A. 인터페이스는 가짜/진짜가 아님. 그냥 이런 기능을 가져야한다는 약속일뿐 구분을 하는게 아님.
>

> Q. 그러면 아까 가짜로 테스트를 하고 싶다고 했는데 이 문제는 인터페이스로는 결국 해결이 안된건가?
>

> A. 결론적으로 맞다. 인터페이스만 만든다고 해서 테스트 문제가 해결되는건 아님 그런데 가짜로 테스트를 하기위해서 마련한 발판이 인터페이스이다. 테스트를 해볼려면 인터페이스, 가짜 구현 클래스, DI 이렇게 세가지가 있어야지 테스트가 가능
>

### DI(의존관계 주입)

위에서 결국에는 진짜 물건을 만들어서 핸드폰에 끼워줘야한다고 했는데 바로 이 행위가 **DI(의존관계 주입)**이다. → 즉 핸드폰 스스로 배터리를 만드는게 아니라 외부에서 이미 만들어진 배터리를 핸드폰에 끼워 넣어주는 방식(핸드폰 배터리 끼우는 구멍만 뚫어놈)

예를 들자면

```notion
class Phone {
    Battery battery; // 1
    // 외부에서 배터리를 넣어주는 통로
    void setBattery(Battery b) { // 2
        this.battery = b;
    }
}

// Phone 밖에서 누군가가
Phone phone = new Phone(); // 3
phone.setBattery(new SamsungBattery()); // 4
```

1: 모든 핸드폰에는 배터리를 꽂을 수 있는 빈칸이 하나씩 있다는 뜻 현재는 아무것도 안꽂혀 있는 빈 슬롯임.

2: 모든 핸드폰은 배터리 끼우기라는 기능을 갖는다는 뜻 → 누군가 나에게 배터리를 하나 건네주면 그걸 내 빈칸에 꽂아넣는 기능

3: 진짜 핸드폰이 하나 만들어짐, 배터리는 아직 비어 있는 상태

4: 진짜 배터리를 하나 만들고 아까 만들어둔 배터리끼우기 기능을 실행하면서 배터리를 건네줌 그리고 배터리 빈칸에 들어감

→ 이렇게 하면 다른 배터리로 바꾸고 싶으면 밖에서 new LG배터리()를 만들어서 끼워주기만 하면됨

**결론 - DI는 내가 쓸 도구를 내가 만들지 않고, 외부에서 만들어서 나에게 넣어주는 방식**

### 주입하는 두가지 방법

1. 생성자 주입 - 객체를 처음 만들때 필요한 걸 한번에 넣어주는 방식
2. 수정자(새터) 주입 - 객체를 만든 다음에 배터리끼우기()와 같은 메소드로 나중에 넣어주는 방식

→ 둘 다 외부에서 넣어준다라는 핵심은 같지만 언제, 어떻게 넣어주는지만 다름

### DI의 더 큰 개념 IoC(제어의 역전)

DI는 사실 IoC(제어의 역전)이라는 더 큰 개념이다. IoC는 원래 스스로 결정하고 제어를 했었는데 DI를 적용하면 이 결정권이 자신이 아니라 외부로 넘어간다. 내가 어떤걸 쓸지 정하는게 아니라 외부에서 누군가 정해준걸 그냥 받아쓰는 것으로 DI는 이 IoC원칙을 의존관계를 주입하는 방식으로 구현한 대표적인 방법
