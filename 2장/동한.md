# Chapter 2장

## 단어 정리

### MVC 계층

**Model**
- 데이터와 비즈니스 로직을 담당
- DB에서 데이터를 가져오거나 저장하는 부분(DAO), 실제 업무 로직(Service) 등이 여기 속합니다
- 화면이 어떻게 생겼는지는 전혀 신경 쓰지 않음

**View**
- 사용자에게 보여지는 화면 담당
- JSP, HTML 같은 것들
- 데이터를 어떻게 예쁘게 보여줄지만 신경 쓰고 데이터가 어디서 왔는지는 몰라도 됨

**Controller**
- 사용자의 요청(예: 버튼 클릭 URL 접속)을 받아서
- 어떤 Model을 실행할지 결정하고
- 그 결과를 어떤 View에 넘길지 연결해주는 "중간 관리자" 역할

이렇게 각 계층을 나눠서 자기 역할만 담당하고 서로 신경 쓰지 않게 만든 구조

**JUnit**
- 자바의 대표적인 테스트 프레임워크

**빌드**
- 개발자가 짠 코드를 모아서 실제로 실행 가능한 프로그램으로 만드는 전체 과정

**빌드 툴**
- 위에서 말한 빌드 과정을 자동으로 해주는 프로그램
- 빌드 툴한테 빌드 과정을 설정 파일로 적어두면 빌드 툴이 알아서 명령 한 번에 과정을 자동화로 처리해줌

**ANT, Maven(메이븐)**
- 대표적인 빌드 툴 이름
- ANT나 메이븐 같은 빌드 툴을 쓰는 프로젝트라면 빌드 툴이 제공하는 JUnit 플러그인/태스크로 테스트 실행 가능

**플러그인**
- Maven에서 쓰는 용어
- 원래 없던 기능을 나중에 끼워 넣어서 추가하는 것

**태스크**
- ANT에서 사용하는 용어
- 빌드 과정을 할 일 목록의 나열로 표현

**엔터프라이즈 애플리케이션**
- 기업이나 조직에서 업무를 처리하기 위해 만드는 규모가 크고 복잡한 소프트웨어를 말함

**JavaEE(Java Enterprise Edition)**
- 자바로 엔터프라이즈 애플리케이션을 만들기 위해 나온 표준 플랫폼/기술 모음

## 2.1.1

스프링 개발자에게 제공하는 가장 중요한 가치는 객체지향과 테스트다.

애플리케이션은 계속 변하고 복잡해져 가는데 이 변화를 대응하는 두 가지 방법이 있다.

- 확장과 변화를 고려한 객체지향적 설계와 그것을 효과적으로 담아낼 수 있는 IoC/DI와 같은 기술
- 만들어진 코드를 확신할 수 있게 해주고 변화에 유연하게 대처할 수 있는 자신감을 주는 테스트 기술

**테스트란**
- 내가 예상하고 의도했던 대로 코드가 정확히 동작하는지 확인해서 만든 코드를 확신할 수 있게 해주는 작업이다. 만약 테스트 결과가 원하는 대로 나오지 않는 경우에는 코드나 설계에 결함이 있음을 알 수 있다.

## 2.1.2

**웹을 통한 DAO 테스트 방법의 문제점**

- 테스트를 할 때 DAO만 만들 뿐만 아니라 MVC 서비스 계층 등 모든 입출력 기능을 대충이라도 코드를 다 만들고 실행을 해야 함
- 중간에 오류가 나면 DAO뿐만 아니라 다른 곳에서도 오류가 생길 가능성이 높아 전체적으로 코드를 검사해봐야 함
- 다른 계층의 코드와 컴포넌트 서버의 설정 상태까지 모두 테스트에 영향을 줄 수 있음

> **Q.** 테스트를 어떻게 만들면 이런 문제를 피할 수 있을까?
>
> **A.** 테스트하고자 하는 대상이 명확하다면 그 대상에게만 집중해서 테스트를 만들자!
> - 한 가지 관심을 집중할 수 있게 작은 단위로 만들어진 테스트로 만들자 → 단위 테스트
> - 일반적으로 단위는 작을수록 좋다.

> **Q.** 개발자가 버그가 발생했을 때 어떻게 빠르게 원인을 찾고 수정이 가능할까?
>
> **A.** 테스트를 자동으로 수행되도록 코드를 만드는 것
> - 자동 수행 테스트는 자주 반복할 수 있다는 장점이 있다.
> - 코드를 수정했을 때 수정 때문에 다른 기능에 문제가 발생하는지 빠르게 확인할 수 있다.

## 2.1.3

**문제점**

- **수동 확인 작업의 번거로움**
   - 테스트를 수행하는 과정과 데이터 준비는 코드로 자동화됐지만 정작 결과를 확인하는 과정은 여전히 사람의 눈에 의존
   - 테스트 수행 자체는 자동이지만 결과 확인은 사람 책임이라 완전히 자동화된 테스트라고 할 수 없음
   - 필드가 몇 개 안 될 땐 괜찮지만 필드가 많아지고 복잡해지면 값이 일치하는지 눈으로 확인하는 게 점점 불편해지고 작은 차이는 놓치고 지나칠 실수 가능성 존재

- **실행 작업의 번거로움**
   - main() 메소드 실행이 간단하긴 해도 DAO가 수십 개로 늘어나면 그만큼 main() 메소드도 수십 개가 됨
   - 게다가 그 결과를 눈으로 확인하고 기록해서 전체 기능이 다 잘 됐는지 종합하는 것도 번거로운 작업 추가

## 2.2.1 수동 확인 작업의 문제 해결

테스트 실행과 데이터 준비는 자동화되어 있었지만 결과는 아직까지 사람의 눈으로 판단해야 함
- 책에 있는 코드에서 `.equals`를 통해서 코드가 직접 두 값을 비교하게 만들었다. 이제 인간은 값 하나하나를 대조할 필요 없이 성공이라는 메시지만 확인하면 됨

## 2.2.2 실행 작업의 번거로움 해결

애플리케이션이 커지고 테스트가 많아지면 일일이 실행하고 결과를 관리하는 게 부담

→ JUnit 사용
- 객체를 만들고 실행하는 건 JUnit이 알아서 함 → 개발자가 직접 main()을 짤 필요 없음

**main() 메소드를 JUnit이 인식할 수 있는 일반 메소드로 바꾸는 두 가지 조건**

- public으로 선언(JUnit은 public 메소드만 테스트로 인식)
- `@Test` 애노테이션 붙이기(JUnit에게 이건 테스트 메소드라고 알려줌)

## 2.3.1 JUnit

- 자바의 표준 테스팅 프레임워크
- 스프링의 핵심 기능인 스프링 테스트 모듈도 JUnit을 기반으로 만들어졌기 때문에 스프링을 익히려면 JUnit은 필수

**장점**
- 직접 만든 테스트보다 단순하게 작성 가능
- 테스트 작성 시 필요한 여러 부가 기능도 제공
- 대부분의 자바 IDE(이클립스 등)는 JUnit 테스트를 손쉽게 실행할 수 있는 기능을 갖추고 있음

## 2.3.2

테스트를 실행할 때마다 매번 DB의 USER 테이블 데이터를 사람이 손으로 지우고 실행해야 했음

> **지워야 하는 이유?**
> - 테스트를 반복 실행하면 DB에 중복된 사용자 정보가 쌓임 → 에러 발생

> **좋은 테스트란?**
> 코드에 변경 사항이 없다면 항상 동일한 결과를 내야 하며 반복 실행했을 때 성공/실패가 오락가락하면 좋은 테스트가 아니다.

**해결 방법**

테스트를 마치고 나면 테스트가 등록한 사용자 정보를 알아서 삭제해서 테스트를 수행하기 이전 상태로 되돌리는 것.

**기능 추가**

- 테이블의 모든 레코드를 삭제하는 기능
- 테이블의 레코드 개수를 돌려주는 기능

**장점**
- 이제 테스트를 몇 번을 반복 실행해도 항상 성공
- 테스트 시작 시 항상 테이블을 깨끗이 비우고 시작하기 때문에 이전에 실행했던 흔적이 남아 있어도 문제가 안 됨
- 사람이 매번 DB를 정리해야 했던 번거로움이 사라짐

> **결론**
> 단위 테스트는 항상 일관성 있는 결과가 보장돼야 한다. DB에 남아 있는 데이터 같은 외부 환경에 영향을 받지 않아야 하는 것은 물론이고 테스트를 실행하는 순서를 바꿔도 동일한 결과가 보장되도록 만들어야 한다.

## 2.3.3

이 절에서는 테스트를 좀 더 보강하는 내용이 나온다.

대충 몇 가지만 확인하고 넘어가면 안 되고 더 다양한 경우를 꼼꼼하게 테스트해야 함
- 한 가지 결과만 검증하고 넘어가는 건 위험
- 평소에는 동작하는 것처럼 보여도 특별한 상황에서 문제가 생기는 코드가 많음

## 2.3.4 테스트 주도 개발(TDD)

- 만들고자 하는 기능의 내용을 담고 있으면서 만들어진 코드를 검증도 해줄 수 있도록 테스트 코드를 먼저 만들고 테스트를 성공하게 해주는 코드를 작성하는 방식

**장점**
- 애초에 "테스트를 성공시키는 코드"만 만들도록 진행되니 테스트를 빠짐없이 만들게 됨
- 코드를 작성하는 시간과 애플리케이션을 검증하는 시간의 간격이 짧음(테스트 먼저 만들고 나면 바로바로 실행해볼 수 있으므로)
- 코드에 대한 피드백을 매우 빠르게 받을 수 있음
- 테스트가 성공하는 걸 보면서 자신감을 갖고 가벼운 마음으로 다음 단계로 넘어갈 수 있음

> **그러나 개발자가 왜 테스트를 잘 만들지 않을까?**
> - 엔터프라이즈 애플리케이션은 테스트 만들기가 어렵다는 인식 때문
> - 실제로 스프링 등장 전에는 JavaEE 애플리케이션 테스트가 매우 힘들었고 구조 자체가 테스트하기 어려운 코드도 많았음
> - → 현재는 스프링 덕분에 테스트하기 편한 구조로 애플리케이션을 만들도록 도와주고 테스트 지원 기능도 풍부함

## 2.3.5 테스트 코드 개선

- 테스트 코드 자체가 이미 자신에 대한 테스트이기 때문에 테스트 결과가 일정하게 유지된다면 얼마든지 리팩토링을 해도 좋음

**해결책**

`@Before` 사용
- JUnit에서 각 테스트 메소드를 실행하기 전에 자동으로 먼저 실행시켜주는 기능
- 일반적으로는 중복 코드를 별도 메소드로 뽑아서 각 테스트에서 호출하게 만들 수도 있지만 여기선 JUnit이 제공하는 기능을 활용

**JUnit이 테스트를 실행하는 순서(7단계)**

JUnit이 테스트 클래스를 가져와 테스트를 수행하는 방식:

- `@Test`가 붙은 public, void형, 파라미터 없는 테스트 메소드를 모두 찾음
- 테스트 클래스의 오브젝트를 하나 만듦
- `@Before`가 붙은 메소드가 있으면 실행
- `@Test`가 붙은 메소드를 하나 호출하고 결과를 저장
- `@After`가 붙은 메소드가 있으면 실행
- 나머지 테스트 메소드에 대해 2~5번을 반복
- 모든 테스트 결과를 종합해서 돌려줌

**픽스처(Fixture)**
- 테스트를 수행하는 데 필요한 값 오브젝트 → 여러 테스트에서 반복적으로 쓰이는 경우가 많아서 `@Before`에서 미리 만들어두면 편리함

## 2.4

`@Before`는 테스트 메소드 개수만큼 반복하는데 테스트 메소드가 많으면 많을수록 반복을 많이 해야 함

## 2.4.1

**해결책**

스프링이 제공하는 테스트 컨텍스트 프레임워크
- 스프링은 JUnit과 함께 쓸 수 있는 전용 도구를 제공해서 간단한 애노테이션 설정만으로 컨텍스트를 한 번만 만들어서 모든 테스트가 공유하게 해줌
- `@RunWith` + `@ContextConfiguration`으로 스프링이 컨텍스트를 딱 한 번만 만들어서 공유하게 함

**장점**
- 테스트 속도 대폭 향상 + 여러 테스트 클래스끼리도 컨텍스트 공유 가능

## 2.5 학습 테스트로 배우는 스프링

**학습 테스트란?**
- 보통은 내가 만든 코드를 검증하려고 테스트를 짜지만 학습 테스트는 다른 사람이 만든 API나 프레임워크의 기능을 테스트 코드로 짜보면서 사용법을 익히기 위해 만드는 테스트

## 2.5.1

**학습 테스트의 장점**

- 다양한 조건에 따른 기능을 손쉽게 확인할 수 있음
- 학습 테스트 코드를 개발 중에 참고할 수 있다
- 프레임워크나 제품을 업그레이드할 때 호환성 검증을 도와준다
- 테스트 작성에 대한 좋은 훈련이 된다
- 새로운 기술을 공부하는 과정이 즐거워진다

## 2.5.2

**지금까지 소개했던 기능들**

- JUnit 테스트 오브젝트 테스트
- 스프링 테스트 컨텍스트 테스트

## 2.5.3 버그 테스트

- 코드에 오류가 있을 때 그 오류를 가장 잘 드러내줄 수 있는 테스트를 말함

**장점**

- 테스트의 완성도를 높여줌
- 버그의 내용을 명확하게 분석
- 기술적인 문제를 해결하는 데 도움이 됨
