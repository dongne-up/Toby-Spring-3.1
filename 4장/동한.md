# 4.1

**SQLException** - 자바 프로그램이 데이터베이스랑 대화하다가(이걸 JDBC라고 부른다.) 뭔가 잘못됐을 때 자바가 만들어서 던지는 에러 덩어리이다.

→ 우리는 이 문제를 어떻게 잘 다룰 것인가에 대해서 배워보겠다.

개발자들이 흔히 저지르는 나쁜 예외 처리사항이 두가지 있다

**예외 블랙홀** - 예외를 잡아놓고 아무것도 안하는것

**무책임한 throws** - 아무 의미 없어 모든 예외를 던져버리는 것

→ 예외는 반드시 복구되거나 명확하게 알려져야한다 조용히 사라지거나 무의미 하게 전파되는 예외는 실패한 예외처리다.

### 예외의 종류

- **Error** - 시스템 자체의 비정상 상황(메모리 부족 등). 애플리케이션이 손댈 수 없는 영역이라 아예 신경 끄는 게 맞다.
- **체크 예외** - 자바 컴파일러가 처리를 강제하는 예외. 어떤 상황이 생길수 있으니 반드시 대응책을 마련해야한다 라는 뜻으로 설계되었다.
- **언체크(런타임) 예외** - 에러 날 수 있지만 굳이 미리 대책 안 써놔도 컴파일은 됨.처리를 강제하지 않는 예외. 개발자가 조심하면 피할수 있는 실수이다.

→ 이런 예외들이 발생하지만 현실에서는 역효과가 나타남. 처리하기 귀찮기 때문에 앞에서 본 예외 블랙홀, 무책임한 throws같은 나쁜 코드들이 양산됨 그래서 요즘 기술들은 점점 복구가능성이 진짜 있을때는 체크예외, 나머지는 다 런타임 예외쪽으로 기울고 있다.

### 예외를 대하는 세가지 행동

- **복구** - 문제를 해결해서 진짜로 정상 흐름으로 되돌리는 것.
- **회피** - 내가 처리할 책임이 없다고 판단해서 호출한 쪽으로 넘기는 것. 다만 이건 역할 분담이 명확할 때만 정당한 선택이지 단지 귀찮아서 던지면 그건 앞서 본 무책임한 회피랑 다를 게 없다.
- **전환** - 회피처럼 밖으로 넘기긴 하는데, 원래 예외를 그대로 넘기지 않고 더 의미 있는 다른 예외로 바꿔서 넘기는 것.
  → 예외가 무슨뜻인지 더 잘 전달하기위해(의미부여) or 번거로운 체크 예외를 언체크 예외로 바꿔서 불필요한 처리 강제를 없애기 위해(포장)

회피와 전환은 차이는 둘다 밖으로 던진다는건 비슷해보이지만 전환은 예외에 새로운 의미를 부여해서 훨씬 적극적인 처리다.

### 실전에서는 어떤 전략을 사용해야할까

- **런타임 예외를 기본값으로 삼아라.** - 서버에서는 하나의 요청이 실패해도 그 요청만 중단시키면 됨, 요청을 복구할 방법도 없음 → 복구 못할 예외는 런타임 예외로 바꿔서 불필요하게 예외 처리를 해서 throws를 강제하지말자.
- **정말 의미가 있고 복구 가능성이 있는 예외만 체크 예외로 남겨라.** → 애플리케이션 로직상 반드시 대응해야 하는 예외(애플리케이션 예외)를 개발자가 놓치지 않도록 체크 예외로 만드는게 낫다.

체크 예외 vs 런타임 예외를 나누는 기준이 자바 언어 스팩이 아니라 이 예외를 만났을때 호출자가 대응을 할 수 있는가에 대한 기준이다.

> Q. 그러면 왜 런타임 예외를 기본값으로 삼는걸까? 그냥 단순해서 그런걸까? 체크 예외는 진짜 중요하기 때문인걸까?
>

> A. 결론적으로는 단순하고 중요한 것의 차이가 아니다.
>

우리가 지금 해결하는 쪽은 SQLException인데 여기서 문제는 이 에러는 **체크 예외**이다. 예를 들자면 SQL문법이 틀린것도 아니고 DB서버가 갑자기 죽어버렸다? → 이건 지금 메소드 안에서 catch문법을 써봐야 고칠방법이 없다. 그냥 에러 났다라고 위로 알리는것 말고는 할 수 있는게 없다. 그런데 이런 경우에도 자바는 대책을 써 놓으라고 하니 개발자들은 어쩔수 없이 catch문을 쓰는데 그 안에 아무것도 안넣고 비워두거나(예외 블랙홀) 아니면 무조건 throws를 붙여서 넘겨서 대충 때워버린다(무책임한 throws). → 오히려 대충 처리하는 나쁜 습관이 생김

### 해결방안

스프링이 내린 결론은 SQLException처럼 어차피 고칠방법이 없는 에러는 강제로 대책을 쓰라고 하지 않게 하고 대신 진짜로 다른 방법으로 대처할 수 있는 에러를 안내라도 해 주기만 하는걸 강제 한다고 한다.(ex) 아이디 중복 → 다른 아이디를 쓰세요 안내라도 해달라는 것)

### 정리

SQLException은 체크 예외로 태어났다 → 근데 실제로 발생하는 원인 대부분(서버 다운, 네트워크 끊김, SQL 문법 오류 등)은 호출한 코드 입장에서 고칠 방법이 없다 → 그런데도 자바는 체크 예외니까 무조건 catch나 throws를 강제한다 → 개발자들은 어차피 할 게 없으니 catch를 비워두거나(블랙홀) 무조건 throws로 던져버린다(무책임한 throws) → 나쁜 습관이 반복된다 → 그래서 스프링은 고칠 수 없는 예외는 강제하지 말고, 진짜 대응 가능한 예외(아이디 중복처럼)만 강제하자는 결론을 내렸고 그 실현 방법이 JdbcTemplate이 SQLException을 자동으로 런타임 예외(DataAccessException)로 바꿔서 던지는 것이다.

# 4.2

여기서 의문점 “그냥 아무런 런타임 예외로 대충 포장하면 끝 아닌가?” → 절대 아님 좀 더 똑똑하게 바꿔야한다라는 취지로 예외를 다른 것으로 바꿔서 던져야함(예외 전환)

### JDBC의 한계 — 왜 SQLException 하나로는 부족한가

- SQL 자체가 DB마다 다르다는 문제. - SQL은 표준 언어이긴 한데, 실제로는 각 데이터베이스 회사(오라클, MySQL 등)마다 자기들만의 고유 문법이나 기능이 있다. 성능을 위해서 이런 비표준 기능을 많이 쓰게 되는데 그러면 DB를 바꾸는 순간 SQL을 전부 다시 써야 하는 문제가 생김
- SQLException 자체가 너무 뭉뚱그려져 있다는 문제. - SQL 문법 오류든, 커넥션 실패든, 중복 키 오류든 JDBC는 이 모든 걸 그냥 SQLException 딱 하나로 던져버림. 그래서 정확히 무슨 문제인지 알려면 에러 코드를 봐야 하는데, 이 에러 코드가 DB 회사마다 완전히 제각각이다.
- SQL표준에 정해진 SQL상태 코드라는 것도 있는데 이것도 드라이버 만드는 회사들이 제데로 안지켜서 믿을수 없다.

→ SQLException 하나만 갖고는 DB가 바뀌어도 흔들리지 않는 유연한 코드를 짤 수가 없다.

```notion
SQL 상태 코드(SQLState) - JDBC 표준 스펙에 정해져 있는 코드
ex)연결이 끊겼다는 상황이면 어떤 DB를 쓰든 상관없이 항상 똑같은 코드(예: 08S01)가 나오게 만들자는 취지이다.
```

### 해결책

- **DB회사별 고유 에러코드를 활용**-  앞에서 말한 SQL상태 코드를 버리고 대신 DB회사별 고유 에러코드를 활용한다. 이건 DB회사가 직접 관리하는 코드라 훨씬 더 일관성있고 신뢰도도 높다. → 이 DB에서 이 에러 코드가 나오면 어떤 의미인지 매핑표를 갖고 있어서 어떤 DB를 쓰든 자동으로 예를 들면 이건 중복 키 에러구나 라고 정확히 해석해서 의미 있는 예외로 바꿔줌.

> Q. 그러면 SQL상태 코드를 사용하면 어떤 DB회사든 똑같은 에러코드를 보여줄텐데 그냥 사용하면 안되는건가?
>

> A. SQL 상태 코드는 이렇게 쓰자고 종이 위에 정해놓은 규칙일 뿐이다. 그런데 그 규칙대로 실제 코드값을 채워 넣는 건 사람(각 DB 회사가 만든 드라이버 프로그램)이 하는 일인. 근데 이 드라이버 만드는 회사들이 그 규칙을 정확히 안 지키고 대충 만들었다는 게 문제다. → 즉 신뢰도가 떨어짐 똑같은 에러코드가 안나타날수 있음 → 그래서 DB회사별 고유 에러코드 활용
>
- DataAccessException 계층구조 - 스프링이 아예 DataAccessException이라는 하나의 큰 예외 체계를 만들어서 JDBC든 JPA든 하이버네이트든(자바 프로그램이 데이터베이스와 데이터를 주고받는 방법) 상관없이 같은 의미의 에러라면 항상 같은 타입의 예외로 던져주게 만듦. → 기술 자체가 다르면(JDBC, JPA, 하이버네이트) 예외의 타입 자체가 완전히 바뀌기에 DataAccessException으로 통일
